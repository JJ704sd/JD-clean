# 运维开发工程师简历筛选 Rubric

- 当前版本：operations-devops-rubric-2026-09-17-v1
- 证据范围：只根据简历中的可定位事实记录，不从职位名称或工具名推断熟练度。
- 评分版本：operations-devops-score-2026-09-17-v1

## 证据强度

| 级别 | 含义 |
|---|---|
| E0 | 未提及相关信息；state 为 not_evidenced |
| E1 | 技能列表、自评、头衔或孤立工具/架构关键词；不足以证明实际能力 |
| E2 | 有明确的系统或项目背景、候选人本人动作、责任边界和运维对象 |
| E3 | 在 E2 基础上还说明方法/取舍、风险控制、验证结果及可核验影响 |

confidence 描述原文抽取与证据归类可靠性，不是胜任概率。可靠性低且影响方向性结论时必须二审。团队指标不能直接归于候选人；未说明分母、时段、基线或归因的数字不能自动升为 E3。

## 固定证据维度

| ID | 维度 | 可接受的 E2/E3 证据 | 不足以单独证明 |
|---|---|---|---|
| OPS-EDU-01 | 第一学历与专业 | 明确第一学历层次、专业及教育经历时间顺序 | 用最高学历替代第一学历；毕业年份推年龄；学校声望；推测专业等价性 |
| OPS-EXP-01 | 相关经验年限 | 任职日期与职责支持的运维/DevOps/SRE/平台工作时段；并行时段只累计一次；5 年及以上是最新 JD 的期望 | 未注明口径的自报年限；把开发年限都算作运维年限；把年限不足或缺失直接当作自动淘汰 |
| OPS-LINUX-01 | Linux 与网络诊断 | 线上 CPU、内存、磁盘、连接数、网络或系统故障的诊断、本人处置和验证 | 只列 Linux、Shell、TCP/IP、排障等词 |
| OPS-ENV-01 | 环境、资源与云平台 | 环境交付、资源开通/扩缩容/回收、VPC/安全组/负载均衡/托管服务等个人运维动作 | 只列 ECS、VPC、RDS、OSS 或云厂商 |
| OPS-DB-01 | PostgreSQL、Redis 与消息队列 | 部署、容量/版本管理、备份恢复、云迁移、故障处置与数据/服务验证 | 只列 PostgreSQL、Redis、Kafka、RabbitMQ 等产品名 |
| OPS-DELIVERY-01 | 容器、CI/CD 与变更 | Docker/Compose 配置，构建测试部署回滚链路、审批/发布留档或恢复验证 | 只列 Docker、Jenkins 或“负责发布” |
| OPS-OBS-01 | 可观测、SLO 与事故闭环 | 指标/日志/告警/巡检、响应分级、SLO/SLI 口径、复盘动作及跟踪关闭 | 只列 Prometheus、Grafana、Loki 或监控平台 |
| OPS-SEC-DR-01 | 安全、凭据、审计与灾备 | 主机基线、最小权限、密钥轮换、生产审计、备份策略、恢复演练与结果 | 只写安全合规、备份或某安全产品 |
| OPS-MODEL-01 | 模型 API 与网关运维 | 配额、限流、超时、供应商切换、密钥轮换、调用追踪、降级和线上结果 | 只调用模型 API、列模型名或做 PoC |
| OPS-RAG-01 | 向量检索、RAG 与 Agent 运行链路 | 检索/Agent 线上路径、追踪、向量数据更新、召回/延迟/错误问题定位和回归 | 只列 RAG、向量库、Agent 或 Prompt |
| OPS-AI-GOV-01 | AI 成本、效果和版本变更 | Token 口径、模型/Prompt 版本、灰度对比、效果回归、回滚和成本结果 | 只声称优化 Token 或改进效果 |
| OPS-AUTO-COST-01 | 自动化、IaC 与资源成本 | 可重复脚本/配置、触发条件、权限与失败处理、使用范围、节省/稳定性或容量结果 | 只列 Shell、Python、Go、Ansible、Terraform |
| OPS-COLLAB-01 | 协作、文档与复盘 | 发布/事故/迁移中的具体协作责任、文档产物、决策和闭环 | “沟通好”“推动力强”自评 |
| OPS-OWN-01 | 项目独立承担与核心责任 | 独立负责或作为核心开发/运维人员承担范围、关键决策、风险/回滚、验收和结果；注明本人边界 | 项目名称、团队成果或“参与/负责”但没有本人动作 |
| OPS-SCALE-01 | 运维项目复杂度与业务/用户规模 | 有系统依赖/集成复杂度，或注明统计周期、分母与峰值口径的业务量/用户量/订单/请求规模；并说明容量、可用性、告警或发布保障等规模相关约束 | 无口径的“高并发/海量用户”；只有公司品牌、团队规模或规模数字而无本人运维参与；仅列本人参与但没有复杂度或规模事实 |
| OPS-AI-BONUS-01 | AI 深度使用与 AI 产品经验 | 在真实工作流中持续使用 AI 并有可核验成效，或有 AI 产品从设计/开发/上线/运营的具体责任、用户与结果 | 只列 ChatGPT/模型名称、零散问答、课程练习或无本人贡献的 PoC |
| OPS-OUTSOURCE-01 | 外包/派遣经历排除信号（非计分） | 简历明确说明候选人以外包、派遣或第三方驻场身份从事开发/运维工作 | 管理供应商、服务客户、项目交付给客户，不能据此推断候选人是外包人员 |
| OPS-OFFICE-IT-01 | 公司电脑与办公 IT 管理 | 设备资产台账、发放/配置/回收，Windows/macOS 与办公软件安装升级、故障排查、备份恢复、重装及入离职交接中的个人动作 | 只列“IT 支持”、办公软件名称或无个人动作的设备管理 |
| OPS-OFFICE-NET-01 | 办公网络与 VPN 管理 | 有线/无线网络与 VPN 的搭建配置维护、远程账号权限、连接/访问/性能故障定位及安全验证 | 只列网络、VPN 或厂商名，没有拓扑、权限、排障或验证事实 |
| OPS-DOMAIN-01 | 物流、供应链或跨境行业经验 | 明确的物流、供应链或跨境业务背景，并能说明本人承担的系统/平台运维关联；作为加分项 | 公司名称、客户名称或“服务行业”但没有明确行业事实或个人关联 |

## 各维度权重与证据覆盖分

下列计分维度权重合计 100 分，用于衡量简历中可核验的证据覆盖程度。当前版本沿用核心生产运维和 AI 链路维度，并新增公司电脑/办公 IT、办公网络/VPN 和物流供应链行业背景维度；最新 JD 的 5 年及以上经验是校准要求，行业背景是加分项。外包/派遣是独立的零权重排除信号，不参与计分。当前 JD profile 仍为草案，因此学历、年限、办公 IT职责和外包规则均须招聘负责人及用人经理双人校准后才可启用；下表目前只是内审基线，不构成已生效规则、录用阈值或候选人排序规则。

| ID | 维度 | 权重 |
|---|---|---:|
| OPS-EDU-01 | 第一学历与专业 | 2% |
| OPS-EXP-01 | 相关经验年限（5 年及以上期望） | 10% |
| OPS-LINUX-01 | Linux 与网络诊断 | 8% |
| OPS-ENV-01 | 环境、资源与云平台 | 7% |
| OPS-DB-01 | PostgreSQL、Redis 与消息队列 | 8% |
| OPS-DELIVERY-01 | 容器、CI/CD 与变更 | 8% |
| OPS-OBS-01 | 可观测、SLO 与事故闭环 | 7% |
| OPS-SEC-DR-01 | 安全、凭据、审计与灾备 | 5% |
| OPS-MODEL-01 | 模型 API 与网关运维 | 5% |
| OPS-RAG-01 | 向量检索、RAG 与 Agent 运行链路 | 4% |
| OPS-AI-GOV-01 | AI 成本、效果和版本变更 | 4% |
| OPS-AUTO-COST-01 | 自动化、IaC 与资源成本 | 3% |
| OPS-COLLAB-01 | 协作、文档与复盘 | 3% |
| OPS-OWN-01 | 项目独立承担与核心责任 | 9% |
| OPS-SCALE-01 | 运维项目复杂度与业务/用户规模 | 3% |
| OPS-AI-BONUS-01 | AI 深度使用与 AI 产品经验 | 3% |
| OPS-OFFICE-IT-01 | 公司电脑与办公 IT 管理 | 5% |
| OPS-OFFICE-NET-01 | 办公网络与 VPN 管理 | 5% |
| OPS-DOMAIN-01 | 物流、供应链或跨境行业经验 | 1% |
| **计分维度合计** |  | **100%** |
| OPS-OUTSOURCE-01 | 外包/派遣排除信号（非计分） | 0% |
| **合计** |  | **100%** |

单项得分 = 权重 × 证据系数：E0=0、E1=0.40、E2=0.75、E3=1.00。`conflicting` 和 `directly_not_met` 状态的单项得分强制为 0。总分对 19 个计分维度直接求和并四舍五入，不按已提供证据重新归一化；缺失维度不会把权重转给其他维度。零权重的外包排除信号单独用于合规核验，不加减分。证据置信度不直接改变分数，低置信度仍按复核规则进入二审。OPS-AI-BONUS-01 只计个人 AI 使用或 AI 产品经验，不重复计算 OPS-MODEL/RAG/AI-GOV 的模型运维证据。OPS-OWN-01 计个人责任边界与决策，OPS-SCALE-01 计项目负载、复杂度和用户/业务规模；OPS-OFFICE-IT-01 和 OPS-OFFICE-NET-01 计办公 IT 的可核验个人责任；OPS-DOMAIN-01 仅作行业加分。同一项目可分别支持不同维度，但需提供对应的不同事实，不能把团队规模直接归因给候选人。

内部等级沿用仓库口径：A≥85，B≥70，C≥55，D≥40，E<40。分数和等级表示证据覆盖，不表示胜任概率、录用概率或适岗结论；E1 即使产生有限分数，能力维度仍只能标记为 `not_evidenced`。不得设置总分推进/淘汰阈值，也不得让分数触发推荐状态或 hard gate。

## 状态和处置

- state 只允许 supported、not_evidenced、conflicting、directly_not_met。supported 至少 E2；E0/E1 只能是 not_evidenced。直接不满足必须有明确反向原文与位置；来源互相矛盾使用 conflicting 并记录 U03_CONFLICTING_FACTS。
- OPS-EDU-01 是简历明示的行政事实维度，明确第一学历/专业可用 E1 标记 supported；用户提出第一学历本科及以上为硬门槛，但 profile 双签批准前仍是拟议门槛，不能据此自动不推进。学历须按第一学历核验，不得以最高学历覆盖。计算机相关专业单独记录，不自动并入该硬门槛。
- OPS-EXP-01 按可核验的相关经历累计，最新 JD 以 5 年及以上为期望，权重 10%；在 provisional profile 下仍不得把年限升级为 must_have 或 exclude_if_evidenced。低于 5 年、简历未写年限或日期不完整都只影响证据覆盖，不得单独触发 hard gate、暂不推进或二审；时间或职责冲突另按不确定性处理。
- OPS-OWN-01 是高权重优先项，不是硬门槛，profile 校验器禁止把它升级为 must_have 或 exclude_if_evidenced。区分“独立承担”“项目核心开发/运维”与团队整体成果，明确候选人本人负责的模块、决策、风险/回滚和验收结果；项目规模事实不能替代个人责任。
- OPS-SCALE-01 是项目规模加分项，不是硬门槛，profile 校验器禁止把它升级为 must_have 或 exclude_if_evidenced。优先记录可观察的规模分母与统计周期（如日均/峰值请求、订单、活跃用户），并至少交代一种相关运维约束或治理动作（如容量压测、峰值告警、依赖可用性、SLO/p95、限流或发布保护）；个人运维参与须可定位，但规模数字不能替代个人责任评分。无通用的绝对“高”阈值；不能按公司名气或团队规模推断。没有规模证据时标记 `not_evidenced`，不列为 key gap，不触发负面建议。
- OPS-OFFICE-IT-01 与 OPS-OFFICE-NET-01 是最新 JD 的明确工作职责，当前仍需 profile 校准；取证时分别核对设备/系统/交接和网络/VPN/权限/安全动作，不把办公支持头衔或工具名当作能力证据。
- OPS-DOMAIN-01 是行业加分项，不是门槛；只有明确物流、供应链或跨境业务事实并能与本人系统工作关联时才记录支持证据。未写行业背景不得列为 key gap。
- OPS-AI-BONUS-01 是加分项，不是门槛，不能升级为 hard gate。深度使用要能说明具体工作流、本人动作、使用频率或覆盖范围及结果；AI 产品经验要能说明产品阶段、本人责任、用户反馈/采用及上线结果。若证据只是模型网关、API、向量检索或 Prompt 运维，应计入 OPS-MODEL/RAG/AI-GOV，不重复计入 AI 产品加分。
- OPS-OUTSOURCE-01 仅在简历明确证明候选人本人有外包/派遣/第三方驻场任职经历时形成排除信号，且只有双签批准后才可用于 `do_not_advance_pending_human`；用户尚未提及或履历表述不清不等于有外包经历，不能据此自动淘汰。供应商管理和面向客户交付不等于候选人外包身份。
- 计算证据覆盖分但不据此判断胜任或跨候选人排序；不使用学校/公司品牌或关键词计数。物流、Kubernetes、服务网格、Terraform/Ansible 都不是默认硬门槛。
- provisional_baseline：只做证据整理和追问；recommendation 固定 second_review，记录 U10_RUBRIC_AMBIGUITY，不输出暂不推进。
- approved_jd：advance_pending_human 仍须人工一审；至少一项基础生产运维维度（Linux、云环境、数据库、交付、可观测或安全）和一项模型 API 或 RAG/Agent 线上运维维度须有 E2/E3 证据；无会改变建议的不确定性，方向性证据置信度不得为 low。
- do_not_advance_pending_human 仅可基于批准 profile 中的简历阶段 hard gate，且简历直接证明不满足。任何“没写”“看起来不够”或单纯关键词缺失都不能触发。
- second_review 用于规则未批准、关键要求缺失且会影响方向、事实冲突、贡献边界不清、解析质量差、岗位/职责归属不清或关键证据置信度低。

## 证据摘录与问题

- 保留最短可核验的原文与章节/页码；不要包含姓名、电话、邮箱等无关个人资料。
- 结论卡的 key_gaps 只记录未提供证据、事实冲突或与已批准 hard gate 的直接反证。已支持维度中的次级信息待确认项应写入面试追问，不能用“完全没有证据”概括。
- 迁移和恢复项目追问数据量、停机窗口、校验、回退条件、恢复演练和责任边界。
- 稳定性项目追问故障基线、告警信噪比、响应时长、SLO 窗口、复盘责任人与行动关闭情况。
- AI 链路追问请求追踪、超时/限流/供应商故障、检索指标、回归集、人工兜底、Token 成本和灰度回滚。
