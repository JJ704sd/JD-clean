# 全栈开发实习生简历筛选 Rubric

- 当前版本：`fullstack-intern-2026-08-24-v4`

## 证据强度

| 级别 | 定义 |
|---|---|
| `E0` | 简历没有相关信息 |
| `E1` | 课程、技能列表、自评或孤立关键词 |
| `E2` | 有项目上下文和可区分的个人实现 |
| `E3` | 在 `E2` 基础上说明具体问题、调试/取舍、完成结果和复盘 |

实习岗位不要求生产规模。`INT-BE-01` 和 `INT-PROJECT-01` 的可靠支持至少需要 `E2`；`E2` 必须在同一项目中包含可归属于候选人的实现动作和对象，不能把课程/技能列表与团队成果拼接成完整项目证据。基础熟悉度和行政事实可以由候选人明确陈述形成 `E1` 支持。`E0` 必须是 `not_evidenced`，后者只能使用 `E0` 或 `E1`。

## 状态与置信度

- `not_evidenced`：完整查看可用简历后仍没有足够证据；不等于候选人不会。
- `conflicting`：简历不同位置对同一事实互相矛盾；必须记录 `U03_CONFLICTING_FACTS` 并进入二审，不能直接作为负面门禁。
- `directly_not_met`：候选人有可定位的明确陈述与已批准行政条件相反；必须保留原文和位置。不能由毕业年份、没有关键词或“未写”推断。
- `confidence` 只描述证据抽取和归类的可靠程度。直接推进所依赖的证据、或负面门禁所依赖的缺口/反证为 `low` 时，使用 `U06_BOUNDARY_CASE` 进入二审。

## 证据矩阵

| ID | 维度 | 简历阶段足够证据 | 不足证据与处理 |
|---|---|---|---|
| `INT-ADM-01` | 在读/专业 | 候选人明确提供，至少 `E1` | 未写且会改变资格时用 `U02`；专业等价性由人判断 |
| `INT-AVAIL-01` | 每周至少 4 天 | 候选人明确提供，至少 `E1` | 未写且会改变资格时用 `U02`；不得从毕业年份推断 |
| `INT-BE-01` | 至少一种后端语言 | 项目中的个人实现，至少 `E2` | 只有关键词时生成基础验证题，不直接当作项目能力 |
| `INT-WEB-01` | HTTP/REST | 明确理解陈述为 `E1`；接口设计/联调项目为 `E2` | 未写可由面试或小型作业验证 |
| `INT-FE-01` | 前端基础 | 明确基础为 `E1`；页面、交互或组件实现为 `E2` | Vue3/TS 是优先项，不是硬门槛 |
| `INT-DATA-01` | 数据库/SQL | 明确基础为 `E1`；表、查询、持久化或缓存实现为 `E2` | Redis 未出现不自动判负 |
| `INT-PROJECT-01` | 完整项目 | 至少 `E2`，能区分个人实现 | 团队贡献不清且可能改变结论时用 `U04` |
| `INT-QUALITY-01` | 工程习惯 | 测试、Git、部署、文档等任一真实实践 | 不要求全部具备；工具列表只有 `E1` |
| `INT-AI-01` | AI 学习潜力 | 实践、学习行动或可解释动机 | 既有 AI 项目不是硬门槛 |
| `INT-DOMAIN-01` | 物流/供应链/电商领域 | 订单、履约、库存、轨迹、计费或电商项目证据 | 优先信号；单独缺失不二审、不判负 |

## 后端优先权重

不计算综合分，也不允许用某一维优势抵消核心缺口。比较证据质量、选择最强匹配和安排验证问题时，按以下顺序处理：

1. 后端基础与实现：`INT-BE-01`、`INT-WEB-01`、`INT-DATA-01`；优先看候选人是否真正写过接口、服务逻辑、表/查询或持久化代码。
2. 完整项目与工程习惯：`INT-PROJECT-01`、`INT-QUALITY-01`；用于确认个人贡献、调试迭代和完成能力。
3. 前端与学习加分：`INT-FE-01`、`INT-AI-01`、`INT-DOMAIN-01`；前端项目证据仍是全栈必要组成，但不能替代后端实现。
4. 行政条件：`INT-ADM-01`、`INT-AVAIL-01`；继续按资格门禁独立处理，不参与能力强弱比较。

该优先级只影响证据排序、推进边界和验证问题，不生成总分或自动排名，也不提高到高级岗的生产标准。

## 处置优先级

先判断是否存在会改变结论的不确定性，再判断明确推进或明确暂不推进。若候选人没有任何编程/项目证据，未写可用性通常不会改变当前判断，不应只为形式送二审。

### `second_review`

出现至少一个决策相关不确定性时使用，包括：

- 解析不可靠；
- 核心项目较强，但在读/每周可用性未写；
- 团队项目个人贡献不清、基础信号冲突或位于推进边界；
- 使用 JD 未列语言但项目能力较强，可能具备迁移性；
- 学校、年级、比赛或项目包装可能成为判断代理；
- 岗位归属或 rubric 本身含糊。
- 任何会支撑推进或负面门禁的证据归类置信度为 `low`；

没有正式实习、缺少 Vue3/TS/Redis/AI 项目、物流领域经历或其他加分项，不触发二审。

### `advance_pending_human`

仅在没有决策相关不确定性，并同时满足以下条件时使用：

- `INT-ADM-01`、`INT-AVAIL-01` 为至少 `E1` 的 `supported`；
- `INT-BE-01`、`INT-PROJECT-01` 为至少 `E2` 的 `supported`；
- `INT-WEB-01`、`INT-FE-01`、`INT-DATA-01` 中至少两个为至少 `E1` 的 `supported`；
- `INT-WEB-01`、`INT-DATA-01` 中至少一个为 `E2` 的 `supported`，证明候选人不仅列出后端语言，还实际完成过接口或数据实现；
- 没有明确行政冲突，缺失的优先项已转为验证问题而非负面理由。

### `do_not_advance_pending_human`

只在没有决策相关不确定性，且满足以下任一条件时使用：

- `INT-ADM-01` 或 `INT-AVAIL-01` 存在 `directly_not_met` 的可定位直接反证；
- 完整查看简历后，`INT-BE-01` 和 `INT-PROJECT-01` 都只有 `E0/E1`，且不存在相反的项目证据。

学校品牌、没有正式实习、没有获奖、缺少 AI/Vue3/Redis 或项目规模小均不能支持负面建议。`conflicting` 必须先二审，不得冒充直接反证。负面建议仍须一审人确认。
