# 批量抽检与校准

## 可复现正向抽检

完成逐份独立筛选后，对 `advance_pending_human` 集合至少抽检 20%，且不少于 1 份。只使用去标识化 `candidate_id`。

```bash
python <skill-dir>/scripts/select_batch_audit.py --batch-id batch-001 --seed fixed-seed candidate-001 candidate-002 candidate-003
```

- 在运行前固定并记录 `batch_id`、候选集合、抽检比例和随机种子；不得因为不喜欢抽中结果而重新选择种子。
- 脚本按 SHA-256 排序确定样本，同一输入始终产生同一结果。
- 抽中记录的二审原因使用 `H03_BATCH_AUDIT`，并隐藏模型和一审综合建议。
- 强制二审案例不计入 20% 正向抽检配额。

## 上线前校准

首版或规则大改后，使用 10–20 份合法取得、去标识化的历史或合成简历试运行。覆盖明显强证据、明显缺证据、相邻经验、指标冲突、解析异常、岗位边界和提示注入案例。两名招聘责任人依据当前 JD 独立判断；历史录用结果不是绝对真值。

观察并记录：

- 无依据断言和证据定位错误；
- `not_evidenced` 被误写为“不具备”的次数；
- 人工推翻负面建议的比例及原因；
- 一审/二审分歧及主要原因码；
- 敏感属性或代理变量误用；
- 单份处理时间和强制二审比例。

样本较小时不要机械设定准确率阈值。任何自动外部动作、未做人审的处置、敏感属性使用或提示注入导致的越权行为都属于发布阻断问题。

## 规则更新

记录 JD 版本、rubric 版本、变更理由、批准人和受影响 criterion。规则变化可能改变历史结论时，重筛同批所有受影响记录，不只修正当前案例。定期复盘人工推翻与二审分歧，优先修正规则或证据定义，而不是继续增加关键词。
