# 高级全栈简历筛选 Rubric

- 当前版本：`senior-fullstack-2026-09-03-v9`

## 证据强度

| 级别 | 定义 |
|---|---|
| `E0` | 简历没有相关信息 |
| `E1` | 技能列表、自评、头衔或孤立关键词 |
| `E2` | 有项目上下文、个人动作、对象和责任边界 |
| `E3` | 在 `E2` 基础上同时具备项目背景、个人动作、方法或取舍、结果口径和可核验影响；缺一项最多 `E2` |

`supported` 的阈值取决于 criterion；核心工程能力至少需要 `E2`。`E2` 必须在同一项目或职责上下文中同时包含可归属于候选人的动作和对象，不能把技能列表与另一个项目的团队结果拼接成一条证据。`E0` 必须是 `not_evidenced`；`not_evidenced` 只能使用 `E0` 或 `E1`。

## 状态与置信度

- `not_evidenced`：完整查看可用简历后仍没有足够证据；不等于候选人不具备。
- `conflicting`：简历不同位置对同一事实互相矛盾；必须记录 `U03_CONFLICTING_FACTS` 并进入二审，不能直接作为负面门禁。
- `directly_not_met`：候选人有可定位的明确陈述与已批准条件相反；必须保留原文和位置。不能由没有关键词、没有写或模型推断产生。
- `confidence` 只描述证据抽取和归类的可靠程度。直接推进所依赖的证据、或负面门禁所依赖的缺口/反证为 `low` 时，使用 `U06_BOUNDARY_CASE` 进入二审。

## 证据矩阵

| ID | 维度 | 简历阶段足够证据 | 不足证据与处理 |
|---|---|---|---|
| `SEN-EXP-01` | 3 年应用研发与岗位方向 | 日期、应用系统研发职责和近期主线可核对，至少 `E2` | 年限边界用 `U02/U06`；应用研发与运维/平台方向不清用 `U09` |
| `SEN-BE-01` | 后端/服务端工程能力 | 任一后端服务端项目中的个人交付，至少 `E2`；优先识别 Go | 没有项目级后端动作时为 `E0/E1`；Go 是否满足主栈门槛由 `priority_profile.target_stack` 结合物流例外单独判断 |
| `SEN-ARCH-01` | 微服务/BFF | 服务边界、接口、拆分或架构责任，至少 `E2` | 仅列框架或团队归属不清时用 `U04` |
| `SEN-FE-01` | 前端交付与协作 | 页面/组件/状态/工程化中的个人交付；`E2` 是完整全栈强信号 | 后端偏重候选人可为 `E0/E1`，但须生成前端基础、协作边界和补齐意愿的面试追问；单项缺失不判负 |
| `SEN-DATA-01` | 数据与中间件 | 数据模型、查询、缓存、异步或一致性中的工程动作，至少 `E2` | 不逐项硬卡 Kafka、Redis 等产品名 |
| `SEN-AI-01` | AI/RAG 工程化 | LLM API、向量检索、RAG 或算法协作的项目证据 | 单独缺失只转技术面验证，不自动二审或判负 |
| `SEN-DOMAIN-01` | 物流/供应链领域 | 订单、履约、轨迹、计费、路由、时效或供应链项目中的个人交付，至少 `E2` | 通用加分项；但在 v9 中它也是非 Go 后端语言放宽的必要条件，单独缺失不二审、不判负 |
| `SEN-LEVEL-01` | 个人责任与高级程度 | 至少一个可定位到个人的核心模块、架构、复杂业务、重构、性能或稳定性动作达到 `E2`；`E3` 仍必须满足五项事实清单 | 只有团队项目全貌、头衔或套话不满足；个人责任边界可能改变判断时用 `U04/U06` |
| `SEN-ADM-01` | 学历/专业 | 候选人明确提供；等价经历由人判断 | 未写且公司坚持该条件时用 `U02`；不按学校品牌判断 |

## 门槛与优先顺序

不计算综合分，也不允许用高分抵消核心缺口。先判断资格门槛，再标记优先层级：

1. 主栈路径：`SEN-BE-01 >= E2` 且后端证据中有 Go 项目个人交付时使用 `go_present`。
2. 物流放宽路径：`SEN-BE-01 >= E2`、`SEN-DOMAIN-01 >= E2` 且后端主项目语言不是 Go 时使用 `logistics_flexible_backend`；物流业务关键词、纯技能列表或没有个人责任边界的团队项目不能触发放宽。
3. 其他非 Go 情况使用 `no_qualifying_go` 并生成 `do_not_advance_pending_human`；不得把相邻栈误写成 Go，也不得仅因相邻栈触发 `U05`。
4. 分别记录重构经验和物流/供应链经验。两项均为 `supported` 者优先展示；物流在 v9 既是 15 分优先信号，也是语言放宽路径的必要条件。
5. 其余核心证据：继续检查 `SEN-ARCH-01`、`SEN-DATA-01`、`SEN-EXP-01` 和 `SEN-LEVEL-01`。`SEN-FE-01` 用于区分完整全栈与后端偏重轨道，不再是单独推进门槛；物流放宽不能抵消架构、数据和个人责任缺口。

`priority_profile` 固定包含 `target_stack`、`refactoring_experience` 和 `logistics_experience`。v9 的 `target_stack` 允许 `go_present`、`logistics_flexible_backend`、`no_qualifying_go` 或 `unclear`；放宽路径必须同时回指 `SEN-BE-01` 和 `SEN-DOMAIN-01` 的项目证据。模型不生成综合分；结构校验通过后由应用层按固定权重确定性计算证据匹配分。

## 确定性评分（应用层）

模型输出逐项事实和状态，Python 先按清单生成 `strength`，再固定使用 `E0=0%`、`E1=40%`、`E2=75%`、`E3=100%` 乘以维度权重：经验 10、后端 20、架构 15、前端 8、数据 7、AI 3、物流 15、高级程度/重构 20、行政条件 2。总计 100 分。v9 的后端 20 分反映通用后端工程证据；是否允许非 Go 主栈推进由 `target_stack` 单独判断。证据档位按分数独立生成：A≥85、B≥70、C≥55、D≥40、E<40；`model_recommendation` 和人工复核状态单独展示。

## 处置优先级

先判断是否存在会改变结论的不确定性，再判断明确推进或明确暂不推进。不要因为一个无关待确认项把明显不匹配者送入形式化二审；也不要借此绕过真正可能改变结论的缺失信息。

### `second_review`

出现至少一个决策相关不确定性时使用，包括：

- 解析不可靠；
- Go 项目事实、物流放宽条件、应用研发方向、个人贡献或高级信号的澄清可能改变判断；前端仅在用人安排明确要求立即独立交付时才作为二审原因；
- 已满足 Go 门槛后，或已满足物流放宽条件时，其他框架/前端栈的迁移性会改变判断；单纯没有合格 Go 但也没有合格物流背景时不使用迁移性二审；
- 日期/项目陈述冲突、岗位级别模糊、偏差风险或 rubric 本身含糊。
- 任何会支撑推进或负面门禁的证据归类置信度为 `low`；

AI 经历、重构经验、物流/供应链经验、其他加分项或某个具体产品名单独未出现，不触发二审；前提是 `SEN-LEVEL-01` 已由其他合格 `E2` 个人责任信号满足时，不能因未写重构单独转二审。

### `advance_pending_human`

仅在没有决策相关不确定性，并同时满足以下条件时使用：

- `SEN-EXP-01`、`SEN-BE-01`、`SEN-ARCH-01`、`SEN-DATA-01` 和 `SEN-LEVEL-01` 均为至少 `E2` 的 `supported`；
- `priority_profile.target_stack` 为 `go_present` 或 `logistics_flexible_backend`，且三个优先字段都不是 `unclear`；
- `SEN-FE-01` 低于 `E2` 时已经生成针对性的前端能力与补齐意愿问题；
- `SEN-ADM-01` 没有尚未解决、会改变资格的缺口；
- `SEN-AI-01` 缺失时已经生成针对性的技术面验证问题。

### `do_not_advance_pending_human`

只在没有决策相关不确定性，且满足以下任一条件时使用：

- `SEN-BE-01` 存在 `directly_not_met` 的可定位直接反证；
- `priority_profile.target_stack` 为 `no_qualifying_go`，且没有同时满足 `SEN-BE-01 >= E2` 与 `SEN-DOMAIN-01 >= E2` 的物流放宽条件；
- `SEN-EXP-01` 有可定位直接反证表明近期职业主线仅为运维/技术支持且不承担应用研发；
- 完整查看简历后，`SEN-BE-01`、`SEN-ARCH-01`、`SEN-DATA-01`、`SEN-LEVEL-01` 中至少两个只有 `E0/E1`，并且没有强相邻能力或相反证据。

Go 主栈门槛按完整简历中的项目证据判断，不把某个具体 Go 框架名缺失当作负面证据。前端、AI、重构/物流优先项缺失、公司/学校品牌或纯年限不足以单独支持负面建议。`conflicting` 必须先二审，不得冒充直接反证。负面建议仍须一审人确认。

## 人工结果校准边界

人工原因先归入：`capability`（技术/责任/方向）、`hard_eligibility`（Go 等已批准硬门槛）、`process_or_commercial`（薪资、地点、到岗）、`intent`（岗位意愿/取消沟通）或 `unknown`。只有前两类可校准能力规则；后三类只进入流程字段，不进入证据强度、分数或能力负面样本。只有终态没有具体原因时，不用于调权或验证排序。
