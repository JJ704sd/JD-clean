# 高级全栈简历筛选 Rubric

- 当前版本：`senior-fullstack-2026-08-25-v5`

## 证据强度

| 级别 | 定义 |
|---|---|
| `E0` | 简历没有相关信息 |
| `E1` | 技能列表、自评、头衔或孤立关键词 |
| `E2` | 有项目上下文、个人动作、对象和责任边界 |
| `E3` | 在 `E2` 基础上说明复杂约束、取舍、生产结果或可量化影响 |

`supported` 的阈值取决于 criterion；核心工程能力至少需要 `E2`。`E2` 必须在同一项目或职责上下文中同时包含可归属于候选人的动作和对象，不能把技能列表与另一个项目的团队结果拼接成一条证据。`E0` 必须是 `not_evidenced`；`not_evidenced` 只能使用 `E0` 或 `E1`。

## 状态与置信度

- `not_evidenced`：完整查看可用简历后仍没有足够证据；不等于候选人不具备。
- `conflicting`：简历不同位置对同一事实互相矛盾；必须记录 `U03_CONFLICTING_FACTS` 并进入二审，不能直接作为负面门禁。
- `directly_not_met`：候选人有可定位的明确陈述与已批准条件相反；必须保留原文和位置。不能由没有关键词、没有写或模型推断产生。
- `confidence` 只描述证据抽取和归类的可靠程度。直接推进所依赖的证据、或负面门禁所依赖的缺口/反证为 `low` 时，使用 `U06_BOUNDARY_CASE` 进入二审。

## 证据矩阵

| ID | 维度 | 简历阶段足够证据 | 不足证据与处理 |
|---|---|---|---|
| `SEN-EXP-01` | 3 年开发、1 年全栈 | 日期与前后端个人职责均可核对，至少 `E2` | 年限或全栈边界可能影响结论时用 `U02`/`U06` |
| `SEN-BE-01` | Go 或 Node.js | 生产项目中的后端个人交付，至少 `E2` | 只有 Java、Python、PHP 等非目标栈或 Go/Node.js 仅为 `E1` 时不满足门槛；不以相邻栈迁移二审豁免 |
| `SEN-ARCH-01` | 微服务/BFF | 服务边界、接口、拆分或架构责任，至少 `E2` | 仅列框架或团队归属不清时用 `U04` |
| `SEN-FE-01` | 独立前端交付 | 页面/组件/状态/工程化中的个人交付，至少 `E2` | 其他成熟前端栈或独立程度不清且可能改变结论时二审 |
| `SEN-DATA-01` | 数据与中间件 | 数据模型、查询、缓存、异步或一致性中的工程动作，至少 `E2` | 不逐项硬卡 Kafka、Redis 等产品名 |
| `SEN-AI-01` | AI/RAG 工程化 | LLM API、向量检索、RAG 或算法协作的项目证据 | 单独缺失只转技术面验证，不自动二审或判负 |
| `SEN-DOMAIN-01` | 物流/供应链领域 | 订单、履约、轨迹、计费、路由、时效或供应链项目证据 | 同一主栈层级内的优先信号；单独缺失不二审、不判负 |
| `SEN-LEVEL-01` | 高级程度与重构 | 至少一个架构、重构、性能、稳定性或生产影响的 `E3`；其中可定位的重构项目单独标为优先信号 | 其他核心强但高级信号边界不清时用 `U06`；没有重构但有其他 `E3` 不单独判负 |
| `SEN-ADM-01` | 学历/专业 | 候选人明确提供；等价经历由人判断 | 未写且公司坚持该条件时用 `U02`；不按学校品牌判断 |

## 门槛与优先顺序

不计算综合分，也不允许用高分抵消核心缺口。先判断资格门槛，再标记优先层级：

1. 主栈硬门槛：`SEN-BE-01` 必须有至少 `E2` 的 Go 或 Node.js 项目证据。完整查看简历后仍没有合格证据时，使用 `no_qualifying_go_or_nodejs` 并生成 `do_not_advance_pending_human`；强 Java/Python/PHP 或其他相邻栈不能改送 `U05`。
2. 主栈层级：`go_present` 高于 `nodejs_only`。只要有合格 Go 证据即归为 `go_present`；Node.js-only 仍可满足门槛，但在同等核心条件下优先级较低。
3. 同层优先信号：分别记录重构经验和物流/供应链经验。两项均为 `supported` 者优先展示；只满足一项时展示该项；缺失不扣除已经满足的核心能力。
4. 其余核心证据：继续检查 `SEN-ARCH-01`、`SEN-DATA-01`、`SEN-EXP-01`、`SEN-FE-01` 和 `SEN-LEVEL-01`；前端广度、重构或物流经验均不能抵消核心缺口。

`priority_profile` 固定包含 `target_stack`、`refactoring_experience` 和 `logistics_experience`。后两项只允许 `supported`、`not_evidenced` 或 `unclear`；`supported` 必须回指 `SEN-LEVEL-01` 或 `SEN-DOMAIN-01` 的项目证据。优先层级用于招聘责任人在同等门槛下安排复核和 shortlist，不生成综合分，也不改变人工审核要求。

## 处置优先级

先判断是否存在会改变结论的不确定性，再判断明确推进或明确暂不推进。不要因为一个无关待确认项把明显不匹配者送入形式化二审；也不要借此绕过真正可能改变结论的缺失信息。

### `second_review`

出现至少一个决策相关不确定性时使用，包括：

- 解析不可靠；
- Go/Node.js 主栈事实、全栈年限、独立前端、个人贡献或高级信号的澄清可能改变判断；
- 已满足 Go/Node.js 门槛后，其他框架/前端栈的迁移性会改变判断；没有 Go/Node.js 本身不使用迁移性二审；
- 日期/项目陈述冲突、岗位级别模糊、偏差风险或 rubric 本身含糊。
- 任何会支撑推进或负面门禁的证据归类置信度为 `low`；

AI 经历、重构经验、物流/供应链经验、其他加分项或某个具体产品名单独未出现，不触发二审；前提是 `SEN-LEVEL-01` 已由其他合格 `E3` 信号满足时，不能因未写重构单独转二审。

### `advance_pending_human`

仅在没有决策相关不确定性，并同时满足以下条件时使用：

- `SEN-EXP-01`、`SEN-BE-01`、`SEN-ARCH-01`、`SEN-FE-01`、`SEN-DATA-01` 均为至少 `E2` 的 `supported`；
- `priority_profile.target_stack` 为 `go_present` 或 `nodejs_only`，且三个优先字段都不是 `unclear`；
- `SEN-LEVEL-01` 为 `E3` 的 `supported`；
- `SEN-ADM-01` 没有尚未解决、会改变资格的缺口；
- `SEN-AI-01` 缺失时已经生成针对性的技术面验证问题。

### `do_not_advance_pending_human`

只在没有决策相关不确定性，且满足以下任一条件时使用：

- `SEN-BE-01` 或 `SEN-FE-01` 存在 `directly_not_met` 的可定位直接反证；
- `priority_profile.target_stack` 为 `no_qualifying_go_or_nodejs`；即使 Java、Python、PHP 等相邻后端栈或系统能力很强，也不豁免此门禁；
- 完整查看简历后，`SEN-BE-01`、`SEN-ARCH-01`、`SEN-FE-01`、`SEN-DATA-01` 中至少两个只有 `E0/E1`，并且没有强相邻能力或相反证据。

Go/Node.js 主栈门槛按完整简历中的项目证据判断，不把单个框架名缺失当作负面证据。AI 经历缺失、重构/物流优先项缺失、公司/学校品牌或纯年限不足以单独支持负面建议。`conflicting` 必须先二审，不得冒充直接反证。负面建议仍须一审人确认。
