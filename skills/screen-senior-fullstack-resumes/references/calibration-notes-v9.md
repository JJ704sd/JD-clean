# 高级全栈 v9 校准记录

## 本次规则变更

v8 将 Go 项目证据作为所有候选人的绝对后端门槛。v9 保留 Go 优先，但增加一条受限的物流背景放宽路径：

- `SEN-BE-01` 先判断通用后端/服务端工程证据，不再只抽取 Go。
- 有物流/供应链项目个人交付且达到 `E2`，并且后端工程证据达到 `E2` 时，Java、Python、Node.js、PHP 或其他服务端语言可以使用 `logistics_flexible_backend`。
- 没有合格物流项目时，非 Go 后端仍使用 `no_qualifying_go`，不能推进。
- 物流业务关键词、技能列表、团队项目全貌和“参与过物流”但无个人动作均不能触发放宽。

## 兼容与验证边界

- v8 及更早记录继续只读校验，不原地改变其 Go 门禁语义；受本次规则影响的记录必须以 v9 重新筛选。
- 放宽路径仍要求经验、后端、架构、数据和高级责任等其余 v9 核心门槛；物流背景不是对所有证据缺口的豁免。
- 物流或后端放宽依据为低置信度、冲突或个人贡献不清时，使用 `U06_BOUNDARY_CASE`/`U03_CONFLICTING_FACTS` 进入二审。
- 后端得分反映通用后端工程证据；主栈路径和是否可推进由 `priority_profile.target_stack` 单独决定，避免把“非 Go”误算成“没有后端能力”。

## 反事实检查

同一候选人满足其他核心条件时：

| 条件 | 处置 |
|---|---|
| Go 后端项目 `E2`，物流有或无 | `go_present`，按核心门槛判断 |
| 非 Go 后端 `E2` + 物流项目 `E2` | `logistics_flexible_backend`，按核心门槛判断 |
| 非 Go 后端 `E2` + 无物流项目 | `no_qualifying_go`，暂不推进待人工确认 |
| 物流项目 `E2` + 后端仅 `E0/E1` | 不能触发放宽，后端证据仍不足 |
| 物流或后端证据 `low`/`conflicting` | 二审，不直接套用放宽路径 |
