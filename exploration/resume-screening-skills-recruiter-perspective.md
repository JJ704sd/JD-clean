# 全栈岗位简历筛选 Skills：招聘者视角方向探索（v0.2）

## 1. 本轮结论

建议构建两个独立 Skill：

- `screen-senior-fullstack-resumes`：高级全栈工程师简历筛选。
- `screen-fullstack-intern-resumes`：全栈开发实习生简历筛选。

二者使用相同的证据协议、合规边界和人工审核门禁，但不能共用一套权重或“经验年限换算表”。高级岗位的核心是生产环境中的复杂度、端到端责任和技术影响；实习岗位的核心是基础、完整做事能力、学习速度和潜力。

Skill 只产生“有证据的筛选建议”，不直接作出录用或淘汰决定，不自动给候选人发信，也不自动回写 ATS 的最终状态。

## 3. 招聘者真正需要解决的问题

简历筛选的目标不是“给简历打一个看起来精确的分数”，而是：

1. 用统一标准快速找出值得进入下一阶段的人。
2. 把每个判断绑定到简历中的可追溯证据，降低印象流判断。
3. 区分“明确不匹配”“简历没有写”“表述冲突”，避免把缺失信息误判为能力不存在。
4. 控制两类错误：高级岗的高成本误推进，以及两个岗位共同存在的优秀候选人误淘汰。
5. 为面试提供待验证问题，而不是假装简历已经证明一切。
6. 让任何负面或不确定结论都能被人复查、解释和推翻。

## 4. 共同设计原则

### 4.1 先证据，后判断

每项标准只允许使用三种证据状态：

- `直接支持`：简历有项目、职责、产出或可核查事实直接支持。
- `未提供证据`：简历没有写，不能等同于候选人不具备。
- `存在冲突`：日期、职责、技术范围或陈述之间有可指出的矛盾。

不得把技能列表里的关键词自动视为实际能力。每个核心判断至少记录：简历原文摘录、所在章节或页码、判断说明和置信度。

### 4.2 JD 是唯一岗位标准来源

正式运行前，把每个岗位的 JD 转换为版本化职位画像：

- `必须项`：确实影响能否胜任且能从简历合理判断的条件。
- `优先项`：可提高排序，但缺失不得自动淘汰。
- `面试验证项`：无法仅凭简历可靠判断的能力。
- `行政确认项`：到岗时间、实习周期等，只在 JD 合法且明确要求时使用。
- `禁止使用项`：与工作无直接关系或可能导致歧视的属性及其代理变量。

Skill 不得自行增加学历、学校、年龄、性别、婚育、籍贯、照片、民族、宗教、健康等筛选条件，也不得从姓名、照片、毕业年份等信息推断这些属性。学校品牌、公司品牌只能作为背景，不能代替能力证据。

### 4.3 不使用“单分数自动裁决”

可以在招聘者已确认后使用维度评分帮助排序，但必须同时展示：

- 各维度证据和缺口；
- 是否触发关键条件；
- 不确定性原因；
- 建议处置及其人工审核级别。

综合分不得覆盖关键证据缺失，也不得直接触发淘汰。

## 5. Skill A：高级全栈工程师

### 5.1 招聘者要找的核心信号

以下维度来自当前 JD，并已在 [高级全栈工程师 JD 证据画像](./jd-profile-senior-fullstack.md) 中拆为可观察证据：

1. **经验基线**：3 年以上开发，其中至少 1 年真实全栈责任。
2. **后端主栈**：Go（Gin/go-zero）或 Node.js（NestJS/Express）的真实项目交付。
3. **BFF 与微服务**：服务边界、接口、架构取舍和扩展性证据。
4. **前端独立交付**：Vue3、TypeScript、Vite、中后台页面与组件化设计。
5. **数据与中间件**：MySQL/PostgreSQL、Redis、Kafka，以及数据模型和接口设计。
6. **AI 工程化协作**：LLM API、向量数据库、RAG 和与算法工程师协作落地的证据。
7. **重构与性能**：复杂业务或计算密集场景中的重构、优化、指标和结果。
8. **端到端与演进能力**：从业务需求到上线运行，以及推动微服务、前端和 AI 工程化演进。

### 5.2 高级岗不能从简历直接下结论的事项

- 仅凭“精通”或工具列表判断深度。
- 仅凭职级、公司名或工作年限判断高级程度。
- 把团队成果全部归因于候选人。
- 从没有写监控、测试或故障经历推断从未做过。
- 根据技术栈不完全相同直接淘汰具备强迁移证据的人。

这些情况应生成结构化面试追问，或进入二审。

### 5.3 建议输出

- 与 JD 必须项的逐项证据对照。
- 端到端责任范围与生产环境证据。
- 最强的 2–3 个匹配信号。
- 关键缺口：分别标记“未提供证据”或“明确冲突”。
- 3–5 个面试验证问题。
- 非最终建议：`建议推进`、`人工二审`、`暂不建议推进—待人工确认`。

## 6. Skill B：全栈开发实习生

### 6.1 招聘者要找的核心信号

以下维度来自当前 JD，并已在 [全栈开发实习生 JD 证据画像](./jd-profile-fullstack-intern.md) 中拆为可观察证据：

1. **行政条件**：本科及以上在读、计算机相关专业、每周至少 4 天；缺失时由人确认，不推断。
2. **后端基础**：Go、Node.js、Java 或 Python 中至少一种，以及项目中的实际实现。
3. **Web 基础**：HTTP、REST、HTML、CSS、JavaScript；Vue3 或 TypeScript 是优先项。
4. **数据基础**：MySQL/PostgreSQL、Redis 和基础 SQL。
5. **项目完成度**：课程、个人、校内、开源、竞赛或实习项目中的个人贡献、调试和结果。
6. **工程习惯**：单元测试、接口联调、部署、文档、Git、Linux 或 Docker 的初步实践。
7. **AI 学习潜力**：LLM API、向量检索和 RAG 的理解、实践或明确学习意愿。
8. **合作与接受指导**：只作为项目线索和面试验证项，不从简历语言风格推断人格。

### 6.2 实习岗需要特别避免的偏差

- 不因缺少正式工作经历而扣分；课程项目、个人项目、开源和社团项目都可成为有效证据。
- 不用学校品牌、学历层次或比赛名气替代能力判断，除非 JD 中有合法、明确且经招聘负责人确认的要求。
- 不把项目视觉包装好等同于技术深度，也不因表达朴素忽视完成度和学习能力。
- 不用高级岗的生产规模标准筛实习生。

### 6.3 建议输出

- 与 JD 基础要求的逐项证据对照。
- 最完整项目的端到端证据。
- 基础、学习速度和工程习惯的信号。
- 需要面试或作业验证的缺口。
- 适合实习生的 3–5 个验证问题。
- 非最终建议：`建议推进`、`人工二审`、`暂不建议推进—待人工确认`。

## 7. 人工校验与不确定简历二次把关

### 7.1 三道人工门禁

**门禁 0：标准发布前审核**

招聘负责人和用人经理共同确认版本化 JD 画像、必须项、优先项、禁止使用项、输出标签和二审触发条件。未确认时 Skill 只能做探索性分析，不能用于批量筛选。

**门禁 1：每份简历的一审确认**

Skill 输出始终是非最终建议。招聘者必须查看证据表并填写 `approved_by`、`approved_at` 和最终处置。Skill 不得自动发送拒绝、邀约或改变 ATS 最终状态。

**门禁 2：不确定简历的独立二审**

触发二审时，由另一名招聘者或用人方进行独立复核。二审先看原始简历和 JD 证据表，尽量不先看一审的综合结论，降低锚定效应。两人结论不一致时，交由指定招聘负责人裁决并记录原因。

### 7.2 强制二审触发器

任一条件成立即进入 `人工二审`：

- JD 必须项属于“未提供证据”，而不是明确不满足。
- 简历日期、职责、项目范围或技术陈述存在冲突。
- OCR、格式或语言问题可能导致信息抽取不完整。
- 候选人处在推进阈值附近，或维度间明显矛盾。
- 技术栈不完全匹配，但存在较强迁移能力证据。
- 高级岗的个人贡献、生产规模或领导力归属不清。
- 实习岗项目真实性、个人贡献或可用性不清。
- 高级岗只有相邻后端技术栈但具备较强微服务、重构或迁移证据。
- 高级岗的 AI/RAG、Vue3/TS/Vite 或全栈时长没有写清，但其他核心工程证据较强。
- 实习岗没有正式实习，但课程、个人或开源项目显示较强完成度。
- 实习岗的在读状态、每周 4 天可用性或个人项目贡献未写清。
- 筛选结果可能受到敏感属性或其代理变量影响。
- 模型置信度低，或不能给出可追溯证据。

## 8. 合规与候选人保护边界

《个人信息保护法》要求个人信息处理具有明确、合理目的，并限于最小范围；自动化决策应透明、公平、公正，个人有权拒绝仅由自动化决策作出重大影响决定；利用个人信息进行自动化决策还属于应事前开展个人信息保护影响评估并记录的情形。参考：[中国人大网《个人信息保护法》](https://www.npc.gov.cn/WZWSREL25wYy9jMi9jMzA4MzQvMjAyMTA4L3QyMDIxMDgyMF8zMTMwODguaHRtbD9yZWY9aW1i)。

《就业促进法》要求用人单位提供平等就业机会和公平就业条件，不得实施就业歧视。参考：[人力资源和社会保障部《就业促进法》](https://www.mohrss.gov.cn/xxgk2020/fdzdgknr/zcfg/fl/202011/t20201102_394626.html?xxgkhide=1)。

因此，两个 Skill 至少要满足：

- 默认隐藏或忽略与岗位无关的敏感信息和代理变量。
- 只处理筛选目的所必需的信息，并设置访问、留存和删除规则。
- 保留 JD 版本、证据、模型输出、人工决定和覆盖原因，便于说明和审计。
- 不作仅由模型完成的最终淘汰或录用决定。
- 在实际部署前由公司法务或隐私负责人确认适用规则；本探索文件不是法律意见。

## 9. 推荐的 Skill 包结构

两个 Skill 各自保持完整、自包含：

```text
screen-<role>-resumes/
|-- SKILL.md
|-- agents/
|   `-- openai.yaml
|-- references/
|   |-- jd-profile.md
|   |-- rubric.md
|   |-- human-review-policy.md
|   `-- output-schema.md
`-- scripts/
    `-- validate_screening_output.py
```

首版脚本只建议验证输出结构、必填证据和人工门禁字段，不建议写一个自动计算最终录用分的脚本。评分和阈值应在获得真实 JD、招聘者标注样本和校准结果后再决定。

## 10. 下一步探索顺序

1. 招聘负责人确认两个 JD 画像末尾列出的解释问题，并签字冻结标准。
2. 用 10–20 份去标识化历史或合成简历做双人独立标注，观察分歧点和误淘汰风险。
3. 根据标注结果冻结 v1 rubric 和二审触发器，再起草两个 Skill 包。
4. 用独立样本验证：证据准确率、人工分歧率、二审率、误淘汰复盘率和处理时间。
5. 试运行期间保持所有最终决定由人确认，并定期抽样复核高置信度结果。

岗位证据画像见 [高级全栈工程师](./jd-profile-senior-fullstack.md) 和 [全栈开发实习生](./jd-profile-fullstack-intern.md)；配套的招聘者校准、二审流程和验收场景见 [recruiter-calibration-and-review-protocol.md](./recruiter-calibration-and-review-protocol.md)；机器可校验的记录基线见 [screening-record.schema.json](./screening-record.schema.json)。
