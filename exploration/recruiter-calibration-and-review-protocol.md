# 简历筛选 Skills：招聘者校准与双人复核协议（v0.1）

## 1. 用途与适用状态

本协议用于把高级全栈工程师和全栈开发实习生的招聘需求转化为可审核的简历筛选规则，并验证两个 Skill 是否能够稳定地产生有证据、可复核、非最终的筛选建议。

已从用户提供的 `招聘计划.md` 导出中取得 2026-08-14 版 JD，并形成 [高级全栈工程师画像](./jd-profile-senior-fullstack.md) 与 [全栈开发实习生画像](./jd-profile-fullstack-intern.md)。本文定义共享流程；具体要求以对应岗位画像为准。未经过招聘负责人和用人经理签字前，不冻结等价能力规则、权重或推进阈值。

## 2. 发布前的 JD 标准化门禁

招聘负责人应与用人经理逐条处理 JD，禁止把原始自然语言直接交给 Skill 自行解释。每条要求都填写以下字段：

| 字段 | 招聘者需要回答的问题 |
|---|---|
| `criterion_id` | 是否有稳定、唯一的编号？ |
| `requirement_text` | JD 原始要求是什么？ |
| `job_relevance` | 为什么它与岗位实际工作直接相关？ |
| `category` | 必须项、优先项、面试验证项、行政确认项还是禁止使用项？ |
| `resume_observable` | 简历能否可靠证明或否定它？ |
| `accepted_evidence` | 哪些具体项目、职责、成果或事实算有效证据？ |
| `insufficient_evidence` | 哪些关键词、头衔或背景不能单独证明它？ |
| `missing_information_action` | 没写时是二审、面试确认，还是不影响推进？ |
| `conflict_action` | 简历信息冲突时如何处理？ |
| `proxy_risk` | 是否可能间接使用年龄、性别、学校品牌等无关代理变量？ |
| `owner` | 谁对该标准及其解释负责？ |
| `approved_by` | 招聘负责人和用人经理是否都已确认？ |

只有同时满足以下条件的条目才可成为简历阶段的“必须项”：

1. 与岗位核心工作直接相关；
2. 招聘负责人能够解释业务必要性；
3. 简历能够较可靠地观察；
4. 已定义“未写”和“明确不满足”的不同处理方式；
5. 不使用受保护属性或不当代理变量；
6. 招聘负责人和用人经理共同确认。

无法在简历中可靠观察的要求，应降为面试验证项，而不是伪装成精确筛选条件。

## 3. 两个岗位的初始证据矩阵

以下矩阵是跨岗位摘要，不是已冻结的评分表。执行时应读取相应岗位画像中的完整 ID、证据定义和二审触发器。

### 3.1 高级全栈工程师

| 维度 | 较强证据 | 不足以单独证明 | 默认不确定处理 |
|---|---|---|---|
| 端到端责任 | 明确说明从需求、设计、实现到上线运行的个人责任和结果 | “参与某系统”“负责开发” | 贡献边界不清时二审并生成追问 |
| 后端与系统 | 数据、并发、性能、一致性、安全或扩展取舍及结果 | 仅列框架、数据库名称 | 有相邻技术深度时评估迁移能力 |
| 前端工程 | 复杂交互、性能、状态、测试、工程化的具体问题与改进 | 仅列 React/Vue 等关键词 | 没写不等于不会，标记待验证 |
| 生产级能力 | 发布、监控、故障、容量、回滚、质量或安全治理证据 | 只写“上线” | 无生产上下文时不得自动判负 |
| 架构复杂度 | 约束、方案比较、权衡、规模和实际影响 | “负责架构”“高并发”无上下文 | 归属或规模模糊时二审 |
| 技术领导力 | 设计评审、标准推动、指导他人、跨团队决策及结果 | 仅有管理头衔 | 个人贡献与团队成果混淆时二审 |
| 技术迁移 | 在不同语言或框架中复用原理并成功交付 | 技术栈名称与 JD 不完全一致 | 不允许按关键词差异直接淘汰 |

### 3.2 全栈开发实习生

| 维度 | 较强证据 | 不足以单独证明 | 默认不确定处理 |
|---|---|---|---|
| 编程与 Web 基础 | 项目中可解释的数据、接口、网络、数据库或前端原理 | 课程名、技能自评 | 转为基础面试验证题 |
| 完整项目 | 能说明问题、个人贡献、实现、调试、测试、部署和复盘 | 项目名或模板项目无贡献说明 | 贡献不清时二审或生成追问 |
| 动手与调试 | 描述具体故障、定位过程和迭代结果 | “学习能力强” | 不因表述朴素直接判负 |
| 工程习惯 | Git、测试、代码结构、文档、协作或部署的实际使用 | 工具列表 | 没写时标记待验证 |
| 学习速度 | 课程外自学、跨技术迁移、开源、持续迭代证据 | 学校或竞赛品牌本身 | 关注行动与产出而非品牌 |
| 合作潜力 | 个人与团队边界清楚，能说明反馈和协作 | 团队项目但无个人贡献 | 贡献不清时二审 |
| 可用性 | 候选人明确写出的到岗时间和实习周期 | 按毕业年份或年龄推断 | 只做行政确认，不自行推断 |

## 4. 运行状态机

```text
简历接收
  -> 文本与版式抽取校验
  -> 按角色证据矩阵评估
  -> Skill 生成非最终建议
  -> 招聘者一审
       -> 证据充分：人工确认推进或暂不推进
       -> 触发不确定性：进入独立二审
  -> 二审完成后对比结论
       -> 一致：招聘者形成最终处置
       -> 不一致：招聘负责人或用人经理裁决
       -> 发现 JD 含糊：修改 rubric 版本并复筛受影响候选人
```

任何阶段都不得自动发送邀约或拒绝，也不得自动写入不可逆的 ATS 最终状态。

## 5. 不确定性原因码

| 原因码 | 含义 | 必须处理 |
|---|---|---|
| `U01_PARSE_QUALITY` | OCR、格式、语言或页面缺失导致抽取不可靠 | 回看原文件；仍不清晰则二审 |
| `U02_MUST_HAVE_MISSING` | JD 必须项未提供证据，但没有明确反证 | 二审，不得按“不满足”处理 |
| `U03_CONFLICTING_FACTS` | 日期、角色、项目或技术陈述互相冲突 | 二审并生成澄清问题 |
| `U04_CONTRIBUTION_UNCLEAR` | 团队成果与个人贡献无法区分 | 二审 |
| `U05_TRANSFERABILITY` | 技术栈不一致但存在较强相邻能力 | 二审，禁止关键词淘汰 |
| `U06_BOUNDARY_CASE` | 处于招聘者确认的推进边界附近 | 二审 |
| `U07_BIAS_OR_PROXY` | 可能受到敏感属性或代理变量影响 | 去除相关信息后重新评估并二审 |
| `U08_DIMENSION_CONFLICT` | 各维度信号明显矛盾 | 二审 |
| `U09_ROLE_AMBIGUITY` | 候选人更像其他级别或相邻岗位 | 二审或转交相邻岗位招聘者 |
| `U10_RUBRIC_AMBIGUITY` | JD/rubric 本身不足以得出一致结论 | 暂停该规则，升级规则负责人 |

“缺少优先项”本身不自动触发二审；只有缺失信息可能改变处置时，才记录为不确定性。

## 6. 独立二审协议

### 6.1 二审输入

二审者应先看到：

- 原始简历；
- 已批准的 JD 画像和 rubric 版本；
- Skill 抽取的逐项证据及来源位置；
- 二审触发原因码。

在完成独立判断前，二审者不应看到一审的综合推荐和最终处置，减少锚定效应。若系统无法隐藏，一审结论应放在证据表之后并默认折叠。

### 6.2 分歧处理

| 分歧类型 | 处理方式 |
|---|---|
| 原文抽取错误 | 修正证据记录，重新执行两人判断 |
| 对候选人证据解释不同 | 用人经理或指定技术招聘负责人裁决 |
| 对 JD 标准理解不同 | 规则负责人澄清并发布新 rubric 版本 |
| 标准本身不合理或含代理偏差 | 暂停该标准，转 HR/合规负责人审核 |
| 仍无法判断 | 保持“待验证”，交由结构化面试或作业，而非强行淘汰 |

如果规则更新可能影响同批其他候选人，应按新版本复筛所有受影响记录，而不是只修正当前候选人。

## 7. 校准试运行设计

### 7.1 样本

- 每个岗位先准备 10–20 份合法取得、去标识化的历史或合成简历。
- 覆盖明显匹配、明显缺证据、技术栈迁移、履历冲突和边界案例。
- 不把历史录用结果直接当作绝对真值；应由两名招聘者依据当前 JD 独立重标。
- 校准样本与最终验收样本分开，避免只针对已知案例调规则。

### 7.2 首版发布硬门槛

以下指标建议设为 100% 或 0 容忍：

- 每项核心判断都有可定位的简历证据，或明确标记为“未提供证据”。
- 所有最终处置均有人类审核记录。
- 所有不确定性触发器均进入二审。
- 没有自动发送邀约、拒绝或不可逆 ATS 操作。
- 没有使用或推断敏感属性及无关代理变量。
- 没有把“未写”记录成“明确不满足”。

### 7.3 观察指标

- 招聘者一审与二审的分歧率及分歧原因。
- 候选人进入二审的比例和主要触发原因。
- 证据抽取错误率、无依据断言数。
- 与纯人工基线相比的单份处理时间。
- 被人工推翻的负面建议比例。
- 结构化面试后发现的误淘汰和误推进模式。

观察指标先用于发现规则问题，不应在样本很小时机械设定统计阈值。

## 8. 必测验收场景

1. 高级候选人技术栈不完全相同，但有强系统设计和跨栈迁移证据：应进入人工评估或二审，不得关键词淘汰。
2. 高级候选人只列大量技术名词，没有个人贡献和生产结果：应标记证据不足并生成验证问题。
3. 实习候选人没有正式实习，但完成了完整项目并能说明调试过程：项目证据必须被正常认可。
4. 实习候选人学校背景普通、项目证据扎实：学校品牌不得降低结论。
5. 简历缺页或 OCR 错乱：触发 `U01_PARSE_QUALITY`，不得继续给出高置信结论。
6. 必须项没有写但没有反证：触发 `U02_MUST_HAVE_MISSING`，不得直接判为不满足。
7. 简历包含照片、性别、婚育或健康信息：相关信息不进入证据和理由，并触发必要的偏差复核。
8. 一审与二审因 JD 含糊产生分歧：触发 `U10_RUBRIC_AMBIGUITY`，更新规则并复筛受影响记录。

## 9. 对两个 Skill 包的映射

每个 Skill 保持自包含：

- `SKILL.md`：只保留角色边界、证据优先、禁止自动裁决、何时读取参考文件等关键行为。
- `references/jd-profile.md`：版本化、已签字的岗位画像。
- `references/rubric.md`：该岗位的证据矩阵、必须项和优先项。
- `references/human-review-policy.md`：本协议中与运行有关的门禁、二审和升级规则。
- `references/output-schema.md`：记录字段及示例。
- `scripts/validate_screening_output.py`：仅验证结构、证据来源、人工审核和二审字段，不计算最终录用结论。

正式 Skill 不应把本探索文档整体塞进 `SKILL.md`。应按渐进披露原则，仅把执行时真正需要的内容放入入口文件和对应 references。

机器可校验的记录基线见 [screening-record.schema.json](./screening-record.schema.json)。该 Schema 已强制：出现不确定性时进入二审、二审记录完成前不能将不确定简历标记为人工最终确认，以及自动外部操作列表必须为空。
